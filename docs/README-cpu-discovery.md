# CPU location discovery

`src/cmn_detect_cpu.py` discovers how Linux CPU numbers map to requesters in
a CMN interconnect. It generates traffic on selected CPUs and counts CMN
watchpoint matches through the Linux `arm_cmn` PMU driver and `perf`.
It can also install known placements using command-line entries or a simple
text file, without taking measurements.

This is separate from [mesh discovery](README-discovery.md), which supplies
the input topology: meshes, crosspoints, device ports, and their identities.
CPU discovery adds the measured CPU locations to that description. The
[object model](README-object-model.md) describes how the resulting CPU
objects relate to the topology; this document describes how they are found.

## What is being discovered?

For each selected Linux CPU, discovery determines:

- The CMN instance, XP, and RN-F device port through which its traffic enters.
- The request's CHI source node ID, recorded as `srcid` in discovery state.
- An LPID, where it is needed and can be established by the discovery policy.

The algorithm must handle a single CPU per port, several CPUs behind one
requester, and several requester devices sharing a port through a CAL.
Finding the port alone therefore does not always identify a CPU. The tool
first separates CPUs by port, then by SRCID, and finally by LPID if necessary.
Every location includes the mesh instance; IDs from different meshes must
not be treated as one identity.

CHI defines SRCID as the packet's source node identity and LPID as a logical
processor identifier within a requester. Importantly, CHI requires an
originating-processor LPID for particular transaction classes, not for all
traffic. A value observed during discovery is not a guarantee that every
request generated by that CPU will carry the same distinguishing LPID.
See the [AMBA CHI specification, IHI 0050E.b, sections 2.2.1 and 2.7](https://documentation-service.arm.com/static/6295e03db334256d9ea8ae86).

CPU mappings obtained by discovery are empirical results for the machine
and configuration being tested. After changes to CPU numbering, firmware,
or the system instance, use verification or update rather than assuming a
previously saved mapping still applies.

## Running discovery

### Prerequisites and effects

Actual measurement requires the target Linux system, a suitable topology
JSON file, a working `perf` command, and permission to use its CMN PMU events.
The command-line tool checks PMU availability before starting discovery.
The [Linux CMN PMU documentation](https://docs.kernel.org/admin-guide/perf/arm-cmn.html)
describes the per-mesh PMUs and watchpoint events.

The default traffic backend also needs a C compiler named `cc` and a
location where temporary executables can run. Its atomic helper is built
for AArch64 with LSE instructions and pthreads. The interval helper uses
`taskset` to select the issuing CPU; an existing lmbench `bw_mem` can replace
that helper via `--lmbench-bin`.

CPU discovery does not open `/dev/mem` or use `cmn_devmem` to program
registers. It does generate CPU and memory traffic and use hardware PMU
resources through the kernel driver. Run it when that disturbance is
acceptable, preferably without competing load or other PMU users. Saved
topology and checkpoint files must be trusted inputs. The current backend
also treats explicit executable-selection options as trusted configuration.

### Common commands

Run these commands from the repository root. `--json` selects the input
file; its usual default is `~/.cache/arm/cmn-system.json`.

```sh
# Discover mappings, or check and refresh existing mappings in this file.
python src/cmn_detect_cpu.py --json topology.json --update

# Check saved mappings without updating the input file.
python src/cmn_detect_cpu.py --json topology.json --verify

# Inspect saved results without generating traffic or checking the PMU.
python src/cmn_detect_cpu.py --json topology.json --report

# Perform fresh measurements, ignoring saved guesses and checkpoint results.
python src/cmn_detect_cpu.py --json topology.json --discard --no-use-checkpoint

# Refresh one CPU while retaining other saved CPU mappings.
python src/cmn_detect_cpu.py --json topology.json --update --cpu 5
```

Choose one main workflow. Do not combine action flags to create additional
modes.

| Workflow | Existing mappings | Result on disk |
| --- | --- | --- |
| Ordinary full discovery | Stops if mappings exist unless `--discard` is supplied. | Writes `--output`, or otherwise an unused `./cmn-system.json`, `./cmn-system-1.json`, etc. |
| `--discard`, full discovery | Replaces mappings after discovery completes; does not use them as guesses. | Writes the input JSON unless `--output` selects another file. |
| `--update` | Uses saved values as measured guesses in atomic mode. | Rewrites the input JSON only if mappings changed or none existed. |
| `--verify` | Requires saved mappings and compares them with the discovered results. | Does not rewrite the input; on a mismatch, attempts to write `./cmn-system-mismatch.json` and exits with status 1. |
| `--report` | Requires saved mappings; performs no discovery. | No output JSON. |

The mismatch diagnostic uses a fixed filename and can replace an earlier
diagnostic. `--output` does not redirect `--update` or `--verify` output.
Normal output writes set `cpu_discovery_time`; an unchanged update does not
refresh the file merely to record that a check occurred.

`--cpu N` selects a single CPU. With `--update`, other cached CPU mappings
are preserved; if there were no cached mappings at all, the tool ignores
`--cpu` and performs full discovery. A targeted `--verify` compares only
that CPU. Without either action, a targeted run reports its result but does
not write a JSON file, even if `--output` or `--discard` was supplied.

Verification can reuse a matching checkpoint. To remeasure everything
selected for verification, also use `--no-use-checkpoint`. `--discard` alone
does not disable checkpoint reuse.

### Measurement controls

| Option | Default | Effect |
| --- | --- | --- |
| `--method` | `atomic` | Tagged atomic requests, or `interval` traffic-volume comparison. |
| `--time` | `0.5` | Nominal measurement workload duration; initial attempts can be shorter and retries longer. |
| `--retries` | `3` | Additional attempts after the first, giving up to four attempts per measurement. |
| `--retry-multiplier` | `3.0` | Multiplies the workload duration for each retry. |
| `--detection-level` | `5.0` | In interval mode, the winning count must exceed this multiple of the next-largest count. |
| `--atomic-batch` | `4` | Maximum issuers in a batch, also constrained by available helper CPUs and buffer space. |
| `--atomic-contenders` | `2` | Helper CPUs reserved for each atomic issuer; zero requests no helpers. |
| `--atomic-min-count` | `1` | Minimum count for an atomic candidate to be considered a match. |
| `--force-discover` | Off | Requests SRCID and LPID probing even when the normal phase policy would infer or omit them. |

`--force-discover` is not a checkpoint-reset option. Use it with
`--no-use-checkpoint` when fresh probes are required. `--diagram` displays
RN-F discoveries on the first mesh and suppresses ordinary progress output;
it applies to full discovery, not the targeted path. Repeated `-v` increases
diagnostic detail. `--perf-bin`, `--lmbench-bin`, and `--keep-exe` configure
the traffic backend. The legacy `-N` argument is parsed but currently unused;
it does not limit the CPU inventory.

## Installing known CPU mappings

If placement is already known, use `--map` or `--map-file` to add, replace,
or delete mappings without generating traffic, checking PMU support, or
using discovery checkpoints. These edits can run on another machine and
include offline CPUs. They require an existing topology JSON description.

```sh
# Update several logical CPUs, retaining all other saved mappings.
python src/cmn_detect_cpu.py --json topology.json --map \
    123=m0:0x380 73=m1:0x400:lpid=2 31=delete

# Apply a file of updates, saving the result separately.
python src/cmn_detect_cpu.py --json topology.json --map-file placement.txt -o mapped.json

# Replace all saved mappings with a complete placement supplied on stdin.
python src/cmn_detect_cpu.py --json topology.json --discard --map-file - < placement.txt
```

Each entry is `CPU=[mM:]ID[:lpid=N]` or `CPU=delete`. `CPU` is the logical
OS CPU number; `M` is the mesh sequence number used in the JSON description
and kernel PMU numbering; `ID` is the CHI source node ID of an RN-F device,
including its device number when a CAL is present. Omitting `mM:` selects
mesh 0. Omitting `:lpid=N` records LPID 0 explicitly. LPIDs are in the range
0..31. Numbers can be decimal or hexadecimal with a `0x` prefix; leading
zeros in decimal numbers do not imply octal.

Mapping files use the same entries, separated by whitespace. Blank lines
and `#` comments are allowed, for example:

```text
# Known placement across two meshes
123=m0:0x380
73=m1:0x400:lpid=2
31=delete
```

`--map` accepts multiple entries and can be repeated. `--map-file` can also
be repeated and combined with `--map`; use `-` to read stdin. A batch can
cover the entire system. Each logical CPU must appear only once across all
inputs. The complete batch is checked before any mappings change: mesh
and RN-F IDs must exist in the cached topology, and the resulting
mesh/ID/LPID identities must be unique. An existing unknown LPID conflicts
with any other CPU at the same mesh/ID until it is replaced or deleted.
CPUs can exchange identities in one batch. Deleting an absent CPU has no
effect. Supplied mappings are validated against topology but are not
verified by measurement.

Manual edits write the input JSON by default; `--output` selects another
file, or `-` for JSON on stdout. Unchanged mappings do not rewrite the input,
but an explicit output is always written. `--discard` removes all saved
mappings before applying the supplied batch; otherwise unmentioned CPUs
are preserved. Manual edits cannot be combined with `--cpu`, `--verify`, or
`--report`. Run `--report` separately to inspect the result, or use
`--verify --no-use-checkpoint` on the target system to check it by measurement.

## How discovery works

Discovery proceeds in three stages for each selected CPU:

1. It generates traffic from the CPU and counts requests entering candidate
   RN-F ports across all meshes. This identifies the mesh, XP, and port.
2. Where a port has several possible requester identities, it counts requests
   with candidate SRCIDs at home-node ports. This stage runs if any RN-F port
   has a CAL, selected CPUs share a port, or `--force-discover` is set.
   Otherwise the selected port's base ID is used.
3. Where CPUs on a port share a SRCID, it probes their LPIDs at that RN-F
   port. `--force-discover` also requests this stage. The automatic search
   covers LPIDs 0 through 15, so a CPU using a higher LPID may not be found.

The default `atomic` method issues tagged atomic requests and looks for a
matching opcode and address tag. It can measure several CPUs together while
locating RN-F ports and LPIDs. Each issuer needs enough available helper CPUs
for its requested contender count. If preparation cannot support an atomic
batch, the tool uses the `interval` method. Atomic measurement can also fall
back to interval measurement if RN-F discovery fails before any selected CPU
has been located; later failures end the run. To select interval measurement
from the start, use `--method interval`.

The `interval` method compares traffic volumes while running a memory-reading
workload on one CPU at a time. It requires a clear winner over other
candidates, so competing traffic can make a result inconclusive. In either
method, a watchpoint match is evidence from the measured workload, not proof
that every request from the CPU uses the same identity. `--time` is a nominal
workload duration; retries may make a run substantially longer.

When CPUs on a port have distinct SRCIDs, the normal discovery policy records
LPID 0 without measuring it. With only one selected CPU on a port, LPID is
normally left unknown. An unknown LPID is omitted from the JSON description;
it differs from an explicit zero. Sharing decisions use only CPUs selected
for this run. For a complete mapping, discover the online CPU population
together. For a targeted investigation, use `--force-discover` to probe a
CPU's additional fields.

## Checkpoints and results

The tool records successful discovery steps in a progress file, normally
`~/.cache/arm/cmn-detect-progress`. If a run is interrupted, a later run can
reuse progress on the same boot when the topology file path, its contents,
and the discovery method match. A checkpoint may still be reused after other
options, the workload, or the set of online CPUs have changed. Use
`--no-use-checkpoint` when those changes call for fresh measurements; this
starts a new recorded run. Completed runs remove their checkpoint. The default
checkpoint filename is shared, so do not run discovery commands concurrently
against it.

The saved JSON records each CPU's mesh, source node ID, and any known LPID.
`--report` shows the saved CPU placements without taking measurements. An
RN-F identity with no mapped CPU means no CPU was mapped there; it does not
by itself indicate a hardware fault.

`--verify` compares new observations with saved placements; on a mismatch it
exits with status 1 and attempts to write `./cmn-system-mismatch.json` without
changing the input file. `--diagram` shows the first mesh, even when discovery
measures multiple meshes.

## Limitations

Results depend on the selected CPU inventory, generated workload, candidate
topology, and successful PMU counter scheduling. A clear count winner cannot
correct an inaccurate input topology. SRCID probing uses home ports in the
issuing CPU's mesh; it does not separately search for home memory on another
mesh. Atomic requests must be visible at the observation points, while
interval measurements can fail under competing traffic. Neither method can
guarantee a distinct observable LPID for every CPU.

For inconclusive results, check the PMU diagnostics, CPU online and affinity
settings, compiler or helper failures, and system load. A longer workload or
smaller atomic batch may help when counts are insufficient. They cannot fix
an absent PMU event, unsupported match field, or ambiguous CPU identity.
Repeated SRCID or LPID clashes can also prevent the final mapping from being
represented uniquely; a failed mapping update is not a successful result.
