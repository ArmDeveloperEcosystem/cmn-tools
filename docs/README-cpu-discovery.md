# CPU location discovery

`src/cmn_detect_cpu.py` discovers how Linux CPU numbers map to requesters in
a CMN interconnect. It generates traffic on selected CPUs and counts CMN
watchpoint matches through the Linux `arm_cmn` PMU driver and `perf`.

This is separate from [mesh discovery](README-discovery.md), which supplies
the input topology: meshes, crosspoints, device ports, and their identities.
CPU discovery adds the measured CPU locations to that description. The
[object model](README-object-model.md) describes how the resulting CPU
objects relate to the topology; this document describes how they are found.

## What is being discovered?

For each selected Linux CPU, discovery determines:

- The CMN instance, XP, and RN-F device port through which its traffic enters.
- The request's CHI source node ID, recorded as `srcid` in discovery state.
- An LPID, where it is needed and can be established by the discovery policy.

The algorithm must handle a single CPU per port, several CPUs behind one
requester, and several requester devices sharing a port through a CAL.
Finding the port alone therefore does not always identify a CPU. The tool
first separates CPUs by port, then by SRCID, and finally by LPID if necessary.
Every location includes the mesh instance; IDs from different meshes must
not be treated as one identity.

CHI defines SRCID as the packet's source node identity and LPID as a logical
processor identifier within a requester. Importantly, CHI requires an
originating-processor LPID for particular transaction classes, not for all
traffic. A value observed during discovery is not a guarantee that every
request generated by that CPU will carry the same distinguishing LPID.
See the [AMBA CHI specification, IHI 0050E.b, sections 2.2.1 and 2.7](https://documentation-service.arm.com/static/6295e03db334256d9ea8ae86).

CPU mappings are empirical results for the machine and configuration being
tested. After changes to CPU numbering, firmware, or the system instance,
use verification or update rather than assuming a previously saved mapping
still applies.

## Running discovery

### Prerequisites and effects

Actual measurement requires the target Linux system, a suitable topology
JSON file, a working `perf` command, and permission to use its CMN PMU events.
The command-line tool checks PMU availability before starting discovery.
The [Linux CMN PMU documentation](https://docs.kernel.org/admin-guide/perf/arm-cmn.html)
describes the per-mesh PMUs and watchpoint events.

The default traffic backend also needs a C compiler named `cc` and a
location where temporary executables can run. Its atomic helper is built
for AArch64 with LSE instructions and pthreads. The interval helper uses
`taskset` to select the issuing CPU; an existing lmbench `bw_mem` can replace
that helper via `--lmbench-bin`.

CPU discovery does not open `/dev/mem` or use `cmn_devmem` to program
registers. It does generate CPU and memory traffic and use hardware PMU
resources through the kernel driver. Run it when that disturbance is
acceptable, preferably without competing load or other PMU users. Saved
topology and checkpoint files must be trusted inputs. The current backend
also treats explicit executable-selection options as trusted configuration.

### Common commands

Run these commands from the repository root. `--json` selects the input
file; its usual default is `~/.cache/arm/cmn-system.json`.

```sh
# Discover mappings, or check and refresh existing mappings in this file.
python src/cmn_detect_cpu.py --json topology.json --update

# Check saved mappings without updating the input file.
python src/cmn_detect_cpu.py --json topology.json --verify

# Inspect saved results without generating traffic or checking the PMU.
python src/cmn_detect_cpu.py --json topology.json --report

# Perform fresh measurements, ignoring saved guesses and checkpoint results.
python src/cmn_detect_cpu.py --json topology.json --discard --no-use-checkpoint

# Refresh one CPU while retaining other saved CPU mappings.
python src/cmn_detect_cpu.py --json topology.json --update --cpu 5
```

Choose one main workflow; the action flags are not mutually exclusive in
the parser, so combinations should not be used as additional modes.

| Workflow | Existing mappings | Result on disk |
| --- | --- | --- |
| Ordinary full discovery | Stops if mappings exist unless `--discard` is supplied. | Writes `--output`, or otherwise an unused `./cmn-system.json`, `./cmn-system-1.json`, etc. |
| `--discard`, full discovery | Replaces mappings after discovery completes; does not use them as guesses. | Writes the input JSON unless `--output` selects another file. |
| `--update` | Uses saved values as measured guesses in atomic mode. | Rewrites the input JSON only if mappings changed or none existed. |
| `--verify` | Requires saved mappings and compares them with the discovered results. | Does not rewrite the input; on a mismatch, attempts to write `./cmn-system-mismatch.json` and exits with status 1. |
| `--report` | Requires saved mappings; performs no discovery. | No output JSON. |

The mismatch diagnostic uses a fixed filename and can replace an earlier
diagnostic. `--output` does not redirect `--update` or `--verify` output.
Normal output writes set `cpu_discovery_time`; an unchanged update does not
refresh the file merely to record that a check occurred.

`--cpu N` selects a single CPU. With `--update`, other cached CPU mappings
are preserved; if there were no cached mappings at all, the tool ignores
`--cpu` and performs full discovery. A targeted `--verify` compares only
that CPU. Without either action, a targeted run reports its result but does
not write a JSON file, even if `--output` or `--discard` was supplied.

Verification can reuse a matching checkpoint. To remeasure everything
selected for verification, also use `--no-use-checkpoint`. `--discard` alone
does not disable checkpoint reuse.

### Measurement controls

| Option | Default | Effect |
| --- | --- | --- |
| `--method` | `atomic` | Tagged atomic requests, or `interval` traffic-volume comparison. |
| `--time` | `0.5` | Nominal measurement workload duration; initial attempts can be shorter and retries longer. |
| `--retries` | `3` | Additional attempts after the first, giving up to four attempts per measurement. |
| `--retry-multiplier` | `3.0` | Multiplies the workload duration for each retry. |
| `--detection-level` | `5.0` | In interval mode, the winning count must exceed this multiple of the next-largest count. |
| `--atomic-batch` | `4` | Maximum issuers in a batch, also constrained by available helper CPUs and buffer space. |
| `--atomic-contenders` | `2` | Helper CPUs reserved for each atomic issuer; zero requests no helpers. |
| `--atomic-min-count` | `1` | Minimum count for an atomic candidate to be considered a match. |
| `--force-discover` | Off | Requests SRCID and LPID probing even when the normal phase policy would infer or omit them. |

`--force-discover` is not a checkpoint-reset option. Use it with
`--no-use-checkpoint` when fresh probes are required. `--diagram` displays
RN-F discoveries on the first mesh and suppresses ordinary progress output;
it applies to full discovery, not the targeted path. Repeated `-v` increases
diagnostic detail. `--perf-bin`, `--lmbench-bin`, and `--keep-exe` configure
the traffic backend. The legacy `-N` argument is parsed but currently unused;
it does not limit the CPU inventory.

## Discovery strategy

### Phase 1: locate the RN-F port

The tool builds upload watchpoints for every RN-F port across all meshes.
It generates traffic from an issuing CPU, compares the candidates, and
records the selected `CMN_RNFPort` wrapper. An upload here means traffic
from the attached device into the XP.

In interval mode the tool probes one CPU at a time and compares traffic
counts. Atomic mode can identify several issuers in a single measurement
by giving each one a distinct address tag. Each atomic issuer must have
exactly one matching candidate.

### Phase 2: establish SRCID

After port discovery, SRCID probing is required for selected CPUs when:

- Any RN-F port in the system has a CAL, or
- Multiple selected CPUs share their RN-F port, or
- `--force-discover` is set.

Candidates come from the selected port's `ids()` method, keeping slot and
ID-layout rules in the topology implementation. When no probe is required
and no SRCID observation is already present, the port's `base_id()` is used.

The probes observe requests at home-node download ports rather than at the
originating RN-F upload port. For example, CMN-700's upload watchpoint
ID field matches TGTID, whereas its download watchpoint ID field matches
SRCID. See the [CMN-700 r3p0 TRM, section 6.1.1.1](https://documentation-service.arm.com/static/64c001a8df6cd61d528c8a55#page=1200).
The implementation delegates product-specific match encoding to `cmnwatch`.

Interval discovery samples at most eight HN-F-property ports in the CPU's
mesh, randomly selected and cached for the session. Counts for the same
SRCID are summed across those ports. If that measurement exhausts its
attempts without a clear result, it tries all home-node ports in that mesh,
unless the first selection already included them all.

Atomic SRCID discovery uses a different optimization. It collects the
distinct XP port numbers occupied by home nodes and builds a mesh-wide
download watchpoint for each such port number and candidate SRCID. These
events select `wp_dev_sel` but no individual XP `nodeid`. The opcode and
address tag restrict the matches, avoiding one event per home-node position.
SRCID discovery itself remains one CPU at a time in both methods.

### Phase 3: distinguish CPUs sharing a SRCID

The tool groups selected CPUs by port and discovered SRCID. If any CPUs on
a port share a SRCID, all selected CPUs on that port become LPID candidates.
`--force-discover` also requests LPID probing regardless of sharing.

LPID probes are upload watchpoints on the known RN-F port. Interval mode
compares counts for the candidate LPIDs; atomic mode also matches the
issuer's opcode and address tag and can batch several CPUs.

The implementation currently searches LPIDs **0 through 15**. This is a
software search limit, not a statement of the architectural field width;
for example the CMN-700 REQ watchpoint has a five-bit LPID field in
[TRM table 6-1](https://documentation-service.arm.com/static/64c001a8df6cd61d528c8a55#page=1200).

When several selected CPUs share a port but have distinct SRCIDs, the
normal policy skips LPID measurement and records zero for them. This is a
discovery convention, not a measured zero. With only one selected CPU on a
port, the policy normally leaves LPID unknown unless an observation already
exists. Unknown LPID is `None`, displayed as unknown and omitted from JSON;
it must not be confused with an explicit zero.

Sharing decisions use the CPUs selected for this invocation, not every CPU
in an existing mapping file. Consequently a targeted run need not reproduce
the LPID work of a full run. Use full discovery to establish sharing across
the online CPU population, or `--force-discover` when deliberately probing
one CPU's additional fields.

## Measurement methods

### Tagged atomic requests

`cmn_traffic_gen` builds a small C program whose issuer threads execute
byte-sized `STEORB` operations. Discovery looks for the corresponding
`AtomicStoreEOR` opcode and an address tag. The intent is to identify a
specific generated request pattern instead of relying on it being much
more frequent than unrelated traffic. It is still an empirical match, not
proof that no other traffic could have the same tag.

Each batch uses a 4096-byte-aligned buffer divided by the helper into 64
slots of 64 bytes. For batch slot `s` and CPU `c`, the implementation uses:

```text
line_index = s
byte_offset = 1 + ((c + s) % 63)
page_offset = line_index * 64 + byte_offset
```

`atomic_addr()` matches the low 12 address bits and masks the higher bits;
it does not need to discover the allocation's full physical address. These
buffer sizes and the mask are implementation choices in the helper and
discovery code and must remain consistent when either is changed.

Contender threads run on other CPUs and perform ordinary stores to a
different word in the issuer's slot. They are intended to create contention
that makes the atomic traffic visible in the mesh. An issuer and its
contenders are pinned to their assigned CPUs. Helpers are allocated from
outside the batch's issuer set, without sharing helpers between entries.
With positive contender count `k`, a batch normally needs `1 + k` online
CPUs per issuer. Zero contenders removes that reservation but may make the
traffic harder to observe.

`atomic_batch_capacity()` limits a batch by the requested size, the 64-slot
buffer, and the CPU inventory. `prepare()` switches to interval mode if
there are not enough online CPUs for even one issuer plus its requested
helpers, or if the requested batch size exceeds the buffer capacity.

### Interval traffic-volume comparison

The default interval helper repeatedly reads a 16 MiB allocation while
pinned to the issuing CPU. With `--lmbench-bin`, it instead runs `bw_mem`.
RN-F selection counts requests without the atomic opcode/address filter;
SRCID and LPID probes add their candidate field filters.

`max_index()` accepts a winner only when its count is strictly greater
than `detection_level` times the runner-up. For example, at the default
factor, counts `[100, 10]` select the first candidate but `[50, 10]` do not.
The one-candidate case is accepted directly, even at zero counts; this is
a shortcut in the implementation, not independent evidence of traffic.

### Event grouping and retries

Discovery distinguishes a logical candidate, a watchpoint for that
candidate, and the perf events encoding that watchpoint. One candidate
may need observations at several ports, and one watchpoint can require
multiple match groups. For combined watchpoints the Linux driver attributes
the count to the primary match, as described in its
[watchpoint documentation](https://docs.kernel.org/admin-guide/perf/arm-cmn.html#watchpoints).

`normalize_logical_events()` and `flatten_logical_events()` preserve this
structure while building the flat event list for perf. The grouping records
the first event of each watchpoint; `group_counts()` sums those representative
counts for each candidate without double-counting combined match groups.

`get_max_event()` handles simple interval comparisons, while
`get_max_logical_event()` handles grouped candidates.
`get_exact_event_batch()` flattens all issuers' candidates into one
measurement, then reconstructs counts separately for each issuer. Its
`sole_index()` rule requires exactly one candidate at or above
`atomic_min_count`; every issuer in the batch must satisfy that rule.
`get_exact_event()` wraps the same path for one issuer.

For `n` perf events and requested duration `t`, the initial workload uses
`min(t, min(0.01, t) * n)` when `n` is positive. Each retry multiplies that
duration by `retry_multiplier`. Thus `--time` is not a maximum elapsed time
or a cap on retries. The backend converts it to helper loop counts rather
than imposing a precise wall-clock sampling interval; compilation and perf
setup also contribute to runtime.

Missing counts or `<not counted>` results raise
`TrafficMeasurementInconclusive`, which the measurement routines retry.
Unexpected count text raises `TrafficMeasurementError`. Exhausted matching
attempts and some subprocess failures raise `SystemExit`. The orchestration
layer decides whether a failure permits a method change or must terminate
the run.

### Atomic fallback and cached guesses

During RN-F discovery, atomic failure permits a restart in interval mode
only if none of the selected CPUs has an RN-F observation yet. Once any
selected CPU has been located, failures propagate instead of mixing methods.
That also means later SRCID or LPID failures do not trigger an automatic
whole-run fallback. An explicit `--method interval` can be used for a new
run when atomic traffic cannot be observed reliably.

For atomic `--update` and `--verify`, saved mappings are candidate guesses,
not accepted measurements. `verify_cpu_rnf_port_guess_atomic()`,
`verify_cpu_srcid_guess_atomic()`, and `verify_cpu_lpid_guess_atomic()` test
one saved value before falling back to the full candidate search. SRCID
and LPID guesses are tested only when their phase requires those fields.
Interval mode does not use this fast path. Switching methods starts a new
checkpoint run and does not carry atomic checkpoint results into interval
discovery.

## Implementation and state ownership

The implementation is in [cmn_detect_cpu.py](../src/cmn_detect_cpu.py).
Its session objects are clients of the topology model, not additional
physical topology components.

| Component | Responsibility |
| --- | --- |
| `CPUDiscoveryOptions` | Per-run method, thresholds, retry policy, helper settings, and verbosity. Library verbosity defaults to zero; the CLI starts at one. |
| `CPUDiscovery` | System reference, copied options, backend, checkpoint, diagram, CPU inventory, event lists, selections, and observations. |
| `CMN_RNFPort` | Session-owned wrapper around a topology port, providing upload events and a list of CPUs observed there. Per-port SRCID sharing information is also kept on the wrapper. |
| `TrafficMeasurements` | Adapter to `cmn_traffic_gen` and `cmn_perfcheck`; supplies the existing backend with the session's settings. |
| `DetectProgress` | Append-only checkpoint records and restoration into a session. |
| `CPUDiscoveryDiagram` | CPU-number annotations from observations, using the shared topology renderer. |
| `main()` | Argument parsing, prerequisite checks, workflow selection, checkpoint lifecycle, reporting, and JSON persistence. |

The important `CPUDiscovery` fields are:

- `system`: the input `cmn_base.System`; existing CPU mappings remain intact
  while observations are collected.
- `online_cpus` and `n_cpu`: the selected host inventory and count used for
  preparation diagnostics and batch planning.
- `rnf_ports`, `rnf_port_events`, and `rnf_port_map`: wrappers, initial
  interval events, and lookup by `(cmn_seq, xp_node_id, port_number)`.
- `selected_hnf_ports`: the per-mesh interval SRCID sampling cache.
- `cpu_rnf_port`, `cpu_id`, and `cpu_lpid`: observations indexed by Linux CPU.
- `completed_cpus`: `None` until all discovery phases finish, then the CPU
  numbers whose observations can be committed.
- `progress` and `diagram`: optional per-session checkpoint and rendering
  objects.

Constructing a session does not measure traffic. `prepare()` resets its
observations, enumerates RN-F ports, builds initial events, and checks the
atomic batching prerequisites. By default it obtains CPU availability from
Linux sysfs and the host CPU count from `multiprocessing`. Tests can provide
`prepare(online_cpus=[...])` to avoid host inventory queries. The delayed
`multiprocessing` import also allows reporting and explicitly supplied
inventories to work under Jython, which lacks that module.

`discover_cpus(cpu=None, expected=None)` runs the three phases and marks
completion. It does not insert, remove, or replace topology CPU objects.
Use `discovered_cpu_mapping(cpu)` to inspect a result as a `CPUMapping`
tuple with fields `cmn_seq`, `xp_node_id`, `port_number`, `srcid`, and `lpid`.
`snapshot_cpu_mappings(system)` creates the corresponding saved-mapping
dictionary, and `verify_cpu_mappings(expected, cpus=None)` returns
`(cpu, expected, discovered)` mismatches, including added or missing CPUs.

`commit_cpu_mappings()` is a separate acceptance step. It refuses to run
before successful discovery, then replaces the System's CPU mappings with
the completed selection. `preserve_others=True` retains existing mappings
for CPUs outside that selection. It uses `System.discard_cpu_mappings()`
and `System.set_cpu()`, including replacement of the mesh's SRCID/LPID
lookup, rather than attaching temporary dictionaries to topology objects.
This is not a transactional rollback mechanism if insertion itself fails;
the preservation guarantee applies while discovery is in progress.

A typical library sequence on the target is:

```python
import cmn_detect_cpu
import cmn_json

system = cmn_json.system_from_json_file("topology.json")
options = cmn_detect_cpu.CPUDiscoveryOptions(method="atomic")
discovery = cmn_detect_cpu.CPUDiscovery(system, options=options)
if not discovery.backend.check_cmn_events():
    raise RuntimeError("CMN PMU events are unavailable")
discovery.prepare()
discovery.discover_cpus()
# Inspect or compare observations here before accepting them.
discovery.commit_cpu_mappings()
```

The constructor copies options, so fallback and verbosity changes do not
alter the caller's configuration object. The default adapter temporarily
sets the traffic generator's perf path, lmbench path, executable-retention
flag, and verbosity, plus the perf checker's perf path. It restores those
settings in `finally`, even when measurement fails. This is sequential
isolation, not thread safety: differently configured concurrent calls are
not supported. The helper executable cache in `cmn_traffic_gen` and the
combined-watchpoint ID allocator in `cmnwatch` also remain process-wide.

The traffic module compiles helpers lazily and caches their paths by mode.
It normally registers removal at process exit; `--keep-exe` retains newly
generated helpers for inspection. Its measurement routines return ordered
counts, leaving candidate selection and retry policy to `CPUDiscovery`.

## Checkpoints, results, and progress display

### Restarting an interrupted run

The CLI uses `DetectProgress` at the application's cache path, normally
`~/.cache/arm/cmn-detect-progress`. It is an append-only, tab-separated file
with these record types:

| Record | Fields after the record type |
| --- | --- |
| `meta` | Absolute input JSON pathname, discovery method, SHA-256 fingerprint of the JSON contents. |
| `rnf` | CPU number, mesh sequence number, XP node ID, port number. |
| `srcid` | CPU number, observed SRCID. |
| `lpid` | CPU number, observed LPID. |

Each new run appends a `meta` record unless resuming. The final run must
match the input pathname, method, and file fingerprint before it is reused.
Earlier matching runs are not used when the final run has a different
identity. The CLI also rejects files whose modification time precedes the
current boot, using `/proc/stat` when available.

`apply()` resolves recorded RN-F locations against the session's wrappers.
Unresolvable ports are ignored, and SRCID/LPID entries are applied only for
CPUs with a resolved RN-F. It populates session observations, not System
CPU objects. RN-F and SRCID observations are skipped by subsequent probes;
interval LPID discovery also skips restored LPIDs. The atomic LPID phase
currently rechecks required LPIDs through its guess/search path rather than
unconditionally skipping a restored LPID.

Unlike guesses from an existing mapping JSON, checkpoint observations can
therefore be reused without fresh measurement. The identity does not encode
every option, workload change, or CPU-online change. Use
`--no-use-checkpoint` when those assumptions no longer hold; it starts a
new recorded run rather than disabling checkpoint recording.

Records are appended and flushed as probes succeed. Inferred base SRCIDs
and default LPIDs are not recorded by the probe routines and are recomputed
when discovery resumes. Failed or interrupted discovery keeps its progress
file. The CLI removes the current checkpoint in `finally` once discovery
and commit have completed, including after a verification mismatch. Because
that completion precedes JSON output, a later output-file failure does not
retain the checkpoint. The default filename is shared: do not run multiple
discovery commands concurrently against the same cache file.

### Persisted results and diagrams

`cmn_json` serializes accepted mappings with `cpu`, `mseq`, `id`, and optional
`lpid` fields. Discovery's `srcid` becomes the JSON `id`. Unknown LPIDs are
omitted. The CLI supplies the CPU-discovery timestamp before writing; neither
the measurement methods nor `commit_cpu_mappings()` write JSON themselves.

The CLI commits completed measurements to its in-memory System before
comparing them for `--verify`, so it can serialize the discovered mapping
in a mismatch diagnostic. This does not update the original input file.
Library clients can compare observations before choosing to commit.

`print_cpu_report()` operates only on persisted topology CPU objects. It
reports CPU count, whether CPUs share RN-F node identities, nonzero LPIDs,
and RN-F device identities with no mapped CPUs. Such an empty identity
means no CPU was mapped there, not proof of a hardware fault.

`CPUDiscoveryDiagram.port_cpu_numbers()` obtains labels directly from
`cpu_rnf_port`. The shared `cmn_diagram` renderer therefore needs neither
discovery policy nor live status queries, and progress updates never insert
temporary CPU objects in the System. The current CLI draws only the first
mesh even though measurements cover all meshes.

## Limitations and maintenance checks

Results depend on the selected CPU inventory, generated workload, candidate
topology, and successful counter scheduling. A clear numerical winner does
not correct an inaccurate input topology. SRCID probing currently uses home
ports in the issuing CPU's mesh; there is no separate cross-mesh home-memory
placement search. Atomic mode needs its tagged operations to be visible at
the selected observation points, while interval mode can fail under competing
traffic. Neither method promises distinct observable LPIDs for every CPU.

When investigating inconclusive results, check the printed PMU diagnostics,
online/affinity availability, compiler/helper failures, and system load.
Longer workloads or smaller atomic batches can help with insufficient
counts. They do not resolve an absent event, an unsupported match field, or
an ambiguous CPU identity. Repeated SRCID/LPID clashes can prevent the final
mapping from being represented uniquely; do not treat a failed commit as
successful discovery output.

Keep localized changes consistent across:

- Port/slot candidate generation in the topology model and watchpoint field
  encoding in `cmnwatch`, checked against the applicable CMN TRM.
- Atomic opcode, byte tagging, buffer geometry, and helper CPU allocation
  in discovery and `cmn_traffic_gen`.
- Candidate grouping and primary-event count attribution.
- Phase skipping, cached-guess checks, and method-specific checkpoint reuse.
- Full versus targeted commit and JSON-writing policy.

The hardware-free regressions in `tests/test_cmn_detect_cpu.py` use synthetic
topologies and an injected backend exposing `cpu_gen_traffic(cpu, events,
time)` and `cpus_gen_atomic_traffic(entries, events, time)`. For CLI tests,
the backend also supplies `check_cmn_events()` and a `verbose` setting.
They cover independent sessions, event grouping, retries, cached guesses,
fallback, SRCID/LPID phase decisions, checkpoints, mapping preservation,
diagrams, and command-line output policy.

From the repository root:

```sh
CMN_DUMP=/dev/null PYTHONPATH=src:tests python3 -B -m unittest test_cmn_detect_cpu test_cmn_base_device_model test_cmn_diagram
CMN_DUMP=/dev/null PYTHONPATH=src:tests python3 -B -O -m unittest test_cmn_detect_cpu test_cmn_base_device_model test_cmn_diagram
CMN_DUMP=/dev/null PYTHONPATH=src:tests python2 -B -m unittest test_cmn_detect_cpu test_cmn_base_device_model test_cmn_diagram
CMN_DUMP=/dev/null JYTHONPATH=src:tests jython -B -m unittest test_cmn_detect_cpu test_cmn_base_device_model test_cmn_diagram
```

These tests do not run perf, compile traffic helpers, or access device memory.
They check implementation behavior and compatibility, not whether a specific
machine exposes enough traffic to identify all of its CPUs.
